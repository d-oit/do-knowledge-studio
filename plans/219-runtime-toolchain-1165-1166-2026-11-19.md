# Plan 219 — Runtime toolchain decision (Node matrix + pnpm 12) — #1165, #1166

Date: 2026-11-19 · Batch: plans/217 PR3 · Branch: `feat/plans-217-3-runtime-security`

## Node.js runtime matrix (#1165)

**Decision: keep Node 22 as the primary CI runtime; validate Node 24 and 26 on
a scheduled matrix (`.github/workflows/runtime-matrix.yml`).** The issue
explicitly permits this when a full per-PR matrix is too expensive: the
primary runtime gates PRs, the scheduled weekly workflow (plus
`workflow_dispatch`, plus every change to the workflow definition,
lockfile, or root manifests) runs install/lint/typecheck/unit/build on
Node 22, 24, and 26 with `fail-fast: false`.

- `engines.node` widens from `>=22.0.0 <25.0.0` to **`>=22.12.0 <27.0.0`**:
  - floor `(>=22.12.0)` — first 22.x line with the current toolchain floor;
  - ceiling `(<27.0.0)` — includes the Node 24 and 26 LTS lines
    (nodejs.org/previous-releases), excludes the unnamed Node 27 line so an
    untested future major never matches.
- No runtime is advertised merely because installation succeeds: the shipped
  matrix is the evidence record, and a matrix RED run must be turned into a
  documented exclusion here (with the upstream issue) before shipping.
- `pnpm/action-setup` reads `packageManager`; cache keys use setup-node's
  `cache: 'pnpm'` (keyed by `pnpm-lock.yaml`), so CI/local majors stay aligned.

## pnpm 10 → 12.17.0 (#1166)

**Decision: upgrade the pin from 10.30.3 to 12.17.0.** Evidence recorded on
2026-11-19 (pnpm.io 12.17.0 release notes: lockfile settings moved to
`pnpm-workspace.yaml`; the package.json `pnpm` field was removed in major 12).

| Check | Result |
|-------|--------|
| `pnpm install --frozen-lockfile` with the 10.30.3 lockfile under pnpm 12 | **Failed by design** — `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`: pnpm 12 no longer reads the `pnpm` field, so the `overrides` hash did not match. This is the settings migration, not dependency drift. |
| Settings migration | `peerDependencyRules`, `overrides`, `ignoredBuiltDependencies`→pnpm 12's `allowBuilds` (via `pnpm approve-builds '!pkg'` deny form), and `auditConfig.ignoreCves` moved to `pnpm-workspace.yaml`. `.npmrc` (`engine-strict`) replaced by `engineStrict: true` in the same file; the file itself deleted. |
| Post-migration `pnpm install --frozen-lockfile` under 12.17.0 | **Passes** (exit 0, "Lockfile is up to date"). |
| Lockfile dependency-graph churn | **Zero**: 1179 packages before, 1179 after; added 0, removed 0, changed 0 (verified by a name→version key diff of the lockfile's dependency document). The only lockfile change is the format restructure: settings/overrides moved out (now sourced from `pnpm-workspace.yaml`) and pnpm 12's **package-manager vendor document** (`packageManagerDependencies` + `@pnpm/exe.*` platform entries) — the pinned manager itself is now lockfile-reproducible. |
| Full quality gate under 12.17.0 | lint ✓, typecheck×3 ✓, unit suites ✓ (all projects), production build ✓ — all exit 0 with `pnpm --version` = 12.17.0. |
| New pnpm-12 facts banked | (1) `managePackageManagerVersions` defaults on: a newer `npx pnpm@X` self-downgrades to the pin unless run with `npm_config_manage_package_manager_versions=false`; (2) `ignoredBuiltDependencies` is replaced by `allowBuilds: {pkg: true/false}` — a bare `pnpm install` ERRORS (`ERR_PNPM_IGNORED_BUILDS`) until `pnpm approve-builds [<'pkg'> \| <!pkg>…]` runs; (3) the lockfile becomes a **two-document YAML**: document 1 = manager pin/vendor metadata, document 2 = the dependency lockfile. |

## Rollback path (#1166)

1. Revert the plan-219 commit (restores `packageManager: pnpm@10.30.3`,
   the `engines` range, the `pnpm` field, `.npmrc`, and the single-document
   lockfile: `git revert <commit> && pnpm install --frozen-lockfile`).
2. If only the lockfile needs regenerating (e.g. after an unrelated merge),
   the pnpm 10 path still reads a pnpm-12 lockfile document **only when the
   settings/overrides sections resolve** — safest is to regenerate with the
   pinned major: `npx -y pnpm@10.30.3 install --lockfile-only` then run the
   gate. Because the pnpm-12 vendor document is additive and the dependency
   graph is identical, a 10-formatted lockfile remains a valid rollback
   target.
3. CI rollback: the runtime-matrix workflow is additive; disabling it
   (or its schedule) does not affect the required check set.
