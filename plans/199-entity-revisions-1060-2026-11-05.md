# Plan 199 — Durable per-entity revision history (#1060)

Status: implemented on `feat/1060-entity-revisions` (2026-11-05).

## Problem

Undo/redo is an in-memory corpus snapshot (`history-snapshot.ts`, Plan 157): it
dies with the tab and cannot answer "what did this note say before the merge?".
Reload, a bad sync merge, or an accidental overwrite had no recovery path for a
single note, and the graph snapshot comparison only covers canvas state.

## Decisions

1. **Revisions live in their own IndexedDB object store**, in the existing
   `dks-canonical` database (`CANONICAL_DB_VERSION = 2`), not in the canonical
   envelope. A corpus save therefore never serializes history, and the envelope
   keeps its single-record, atomic-write shape. This overrides the AGENTS.md
   localStorage note for this feature: localStorage still carries only metadata.
2. **Capture is content-keyed and throttled per entity.** `save` revisions keep
   at most one per `REVISION_THROTTLE_MS` (5 min); `merge`, `import`, and
   `restore` are discrete events and always kept when the content actually
   differs. Equality ignores `updatedAt`, so a timestamp-only write is not a
   version.
3. **Capture cannot fail the save path.** Every storage error is logged and
   dropped; `captureEntityRevision` resolves `false` rather than rejecting, and
   the store calls it fire-and-forget. A quota error costs history, never a note.
4. **Retention is count + daily milestones + a byte budget.** An entity keeps its
   newest `MAX_REVISIONS_PER_ENTITY = 20` plus one milestone per day (up to 14
   days beyond the window); the whole store is evicted oldest-first until it fits
   `MAX_REVISION_BYTES = 4 MiB`. Eviction is planned purely (`planEvictions`) so
   the policy is testable without IndexedDB.
5. **A sync merge keeps the pre-merge version first.** `applyRemoteUpdate` records
   the local record with reason `merge` before overwriting it, which is the
   "before the merge" state the issue asks for.
6. **Restore is a normal store write.** `restoreEntityRevision` writes the old
   content as the current entity, pushes one history snapshot (so Undo returns to
   the pre-restore text), and records the pre-restore version as a `restore`
   revision. Restoring is therefore reversible both ways.
7. **Revisions are not exported.** OKF export reads the entity corpus, and
   `.dksb` backups enumerate the envelope's keys, so history stays local by
   default. Optional backup inclusion is deferred (see Known gaps).

## Delivered

- `src/lib/studio/revision-model.ts`: schema, reasons, throttle, retention plan,
  usage summary.
- `src/lib/studio/revision-diff.ts`: metadata diff plus a bounded LCS line diff.
- `src/lib/studio/revision-storage.ts`: IndexedDB append/list/delete/usage, with
  schema validation on read.
- `src/lib/studio/revision-capture.ts`: throttle state, retention enforcement,
  fail-closed capture, fire-and-forget helper.
- `canonical-storage-idb.ts`: DB version 2 with the `revisions` store and
  `by-entity` / `by-created` indexes.
- `slices/entities-slice.ts`: capture on `saveEntity` / `commitEntity` /
  `commitEntities`; new `restoreEntityRevision` action.
- `sync/bridge.ts`: pre-merge revision capture in `applyRemoteUpdate`.
- `components/studio/views/editor-revisions-panel.tsx` +
  `use-restore-entity-revision.ts`: list, usage, diff, restore; mounted under the
  claims panel in the editor.
- `lib/i18n/messages/revisions.ts`: all user-facing strings.
- Tests: model/retention, diff, storage (fake-indexeddb: persistence across
  reopen, malformed-record skip, throttle, per-entity eviction, byte budget), and
  `revisions.bench.test.ts` for capture cost.

## Verification

- `pnpm run test`: all suites pass, including the four new revision suites.
- `pnpm run test:bench`: capture decision 200× on a 50k-character note, 500
  signature comparisons, and eviction planning for 1000 revisions all inside
  their budgets.
- `pnpm run lint`, `pnpm run typecheck`, `pnpm typecheck:test`, `pnpm run build`.

## Known gaps

- **Import tagging is deferred.** Imports that overwrite existing entities are
  captured as `save` revisions (they go through `commitEntities`), not labelled
  `import`; the sync-merge label is the one the acceptance criteria require.
- **Backup inclusion is deferred.** Revisions are excluded from `.dksb`, so
  restoring a backup restores the corpus, not its history.
- **Storage usage is shown per entity, not in Settings.** The panel reports
  `count · bytes`; a global usage row in Settings would need the settings view to
  read the revision store asynchronously (a follow-up).
