# 161 — Offline First-Use Navigation for Lazy Views, Then a Stable Framework Refresh

> Closes the offline half of Plan 158's PWA work: the precache manifest was
> derived from the boot document alone, so five of six code-split views could
> not load on a first offline navigation. Behavior decision: ADR 041.

**Date**: 2026-09-30
**Method**: GOAP (Goal-Oriented Action Planning)
**Status**: Complete — defect reproduced, fixed, regression-proofed, framework
refreshed, and verified end-to-end in production builds (see
[Verification](#verification))

## Problem

`AppShell` code-splits Graph, Mind Map, AI Harness, TRIZ, Export and Sync
(`src/components/studio/app-shell.tsx:30-35`). The service worker's precache
list was generated by scraping `/_next/static/...` URLs out of
`.next/server/app/index.html` — the boot document's own chunks. A lazily
imported view appears in **no** HTML, so its chunk was never precached.

Consequence: a user who installed the app, then went offline and navigated to a
view they had never opened online, had the dynamic import reject. React's view
error boundary rendered `"<View> failed to load"` — the local-first promise
broken at exactly the moment it is being relied on.

| View | Chunk string present in | Precached before |
|---|---|---|
| Graph | `1di-6pjehj6-g.js` | no |
| Mind Map | `15ufv5b5u92pv.js` | no |
| AI Harness | `2wnw_oy1f3wc3.js` | no |
| TRIZ | `06-9k-jk7oovd.js` (i18n only), `0jdw1zmyhz6cz.js` | partially |
| Export | `401_givuphw-a.js` | no |
| Sync | `0rm1p7_b3ef1s.js` | no |

Measured on the pre-fix production build: **17 of 36** emitted chunk files were
in `public/precache-manifest.json`.

## Reproduction (before any fix)

New spec `e2e/offline-views.spec.ts` plus a production run mode in
`playwright.config.ts` (`PLAYWRIGHT_PRODUCTION=1` → `pnpm run start`,
`reuseExistingServer: false`, production-only spec excluded from the default
dev run and from every non-Chromium project).

Intent of the harness: install the worker against a production build, close the
online page so its in-memory modules cannot answer the import, clear the browser
HTTP cache over CDP, then go offline and navigate to the view **for the first
time** in a fresh context.

`pnpm run build && pnpm run test:e2e:offline` — pre-fix result, 6/6 failed, each
for the stated reason:

```
heading "Graph failed to load" [level=2]
heading "Mind Map failed to load" [level=2]
heading "AI Harness failed to load" [level=2]
heading "TRIZ Matrix failed to load" [level=2]
heading "Export failed to load" [level=2]
heading "Sync failed to load" [level=2]
```

### Assertion scoping defect found by the first run

The first version of the spec asserted `getByRole('heading', { name: 'AI Harness' })`
unscoped. The topbar renders `<h1>{meta.title}</h1>` with the current view's
name (`src/components/studio/topbar.tsx:87,11-21`), so AI Harness and Sync
**passed against the error fallback** — chrome satisfied the assertion. All six
assertions are now scoped to the `main` landmark, which is where the view body
renders and where the topbar is not. That change took the reproduction from
"4 fail" to the true "6 fail".

## Fix

### Manifest scope: the emitted code, not just the boot document

`scripts/generate-precache-manifest.mjs` now unions three sources: the boot
document's URLs (unchanged), every `.js`/`.mjs`/`.css` under
`.next/static/chunks`, and fonts/images under `.next/static/media`. Names come
from the real build directory, so a renamed hash cannot silently fall out.
Deliberately excluded: `.wasm`, model weights, source maps, raw `.ts` — media
the user opts into, not app code, one item of which exceeds the whole chunk set.

Generator hardening: the missing-build path is preserved, and the run now fails
with an actionable message when either static directory is absent or the chunk
inventory holds no JavaScript, instead of silently writing a boot-only manifest.
An empty font/image set stays valid.

Result: **61 URLs** (21 document, 36 chunks, 17 media). Measured cost: the whole
chunk set is ~4 MiB, accepted rather than classifying minified chunks by feature.

### Worker identity: `dks-static-v3`

`public/sw.js` changes one constant. The manifest is fetched by the worker at
install time, so an existing installation would otherwise never reinstall with
the widened list — the bytes must change for the browser to notice. Cache
deletion stays in the worker's `activate` handler; `STATIC_EXTENSIONS` and the
API cache are untouched.

## Framework refresh (separate diff, same rollout)

`next` 16.3.6 → 16.3.7, `eslint-config-next` 16.3.5 → 16.3.7, `react` and
`react-dom` 19.2.8 → 19.3.0, `@types/react` 19.2.18 → 19.3.0, `@types/react-dom`
19.2.4 → 19.3.0. TypeScript stays on 6.0.3: typescript-eslint supports
`>=4.8.4 <6.1.0`, so TypeScript 7 is a separate side-by-side tooling migration,
not a drop-in. Zustand untouched at 5.0.15.

Lockfile diff reviewed line by line: the only resolved `package@version` changes
are `next`, `eslint-config-next`, `react`, `react-dom` and their `scheduler`
dependency; the only specifier changes are the six intended ones. All `pnpm`
overrides, peer rules and ignored-build settings are retained.

### Follow-on discovered (pre-existing, not fixed here)

Under `prefers-reduced-motion: reduce`, Home logs a React hydration mismatch for
every framer-motion element in `home-view.tsx`:

```
<motion.section initial={false} animate={{opacity:1}} transition={{duration:0}}>
  <section className="mb-8 flex ..."
+   style={{opacity:1}}
-   style={{opacity:"0"}}
```

`initial={reducedMotion ? false : { width: 0 }}` makes the client's first render
apply the `animate` targets, while SSR can only emit the pre-animation values.
The no-preference path is unaffected, which is why a normal browser session never
sees it.

Measured A/B, same spec, same machine:

| Dependencies | Warnings from `touch-targets.spec.ts --project=chromium` |
|---|---|
| Next 16.3.6 / React 19.2.8 (pre-refresh) | 8 (one per test) |
| Next 16.3.7 / React 19.3.0 (this change) | 8 |

Identical counts, so the framework refresh did not introduce it; the refreshed
versions do not fix it either. Reproduction:
`pnpm exec playwright test e2e/touch-targets.spec.ts --project=chromium` with
`dev.log` watched — that spec sets `contextOptions: { reducedMotion: 'reduce' }`,
and `zoom-reflow.spec.ts` / `accessibility.spec.ts` trigger the same path via
`page.emulateMedia`.

Not fixed in this plan: it is an unrelated UI change (the fix is to give the
motion elements server-resolvable initial values, or to gate them on a
post-hydration flag), and the plan scoped UI work out. Tracked here as the
follow-up the repo's warning policy requires.

### Notes for the next reader

- The manifest is regenerated at deploy time: `vercel.json` runs
  `pnpm run build`, which chains the generator. The committed
  `public/precache-manifest.json` is therefore repo hygiene plus the artifact any
  non-Vercel/static deploy would serve — but it must never be the *reason* a
  chunk is missing, so the fail-closed checks in the generator are what actually
  hold the line.
- The smoke drove the `browser` device for the fresh-profile run and had to
  pass `app.path` + `--headless=new`; its shared managed browser ignores
  `--user-data-dir`. Profile isolation is the point of that run, so the profile
  flag is mandatory, not cosmetic.
- Two smoke assertions were first satisfied by shell chrome rather than view
  content (`waitForText('TRIZ Contradiction Matrix')` matched a seeded entity,
  `main h2` matched the right panel's `Search`). The committed spec avoids this
  class entirely by asserting role-scoped locators inside `main`.
- Wiring `test:e2e:offline` into CI is deliberately **not** part of this change:
  it needs a production build, and the plan scoped CI untouched. ADR 041 records
  the trigger for adding it (any change to the worker, the manifest scope, or
  boot wiring).
